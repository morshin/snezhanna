# TZ-04: Email credentials at rest + TLS verification

**Source:** audit 2026-07, security findings #1 and #2 — the top trust-model
issues for the "instances for friends" scenario.
**Effort:** ~2 evenings including migration.

## Problem

1. **Plaintext credentials, replicated to the cloud.**
   `email_accounts.credentials` (`lib/db.js:191`) stores IMAP passwords and
   Gmail OAuth tokens as plaintext JSON. The SQLite DB is backed up daily to
   Google Drive (`backups/snezhanna_YYYYMMDD.db`, keep 7). So a tenant's mail
   password lives in cleartext: on the VPS, in the bot's Google account, in 7
   rotating copies. Anyone with Drive access to the bot account (or a leaked
   backup) gets working mail passwords.

2. **TLS verification disabled everywhere.**
   `rejectUnauthorized: false` appears in all 4 IMAP connection sites and in the
   SMTP config (`lib/imap.js:31,80,142,190,237`) plus the Mini App connection
   test (`lib/api.js:688`). Any MITM can present a self-signed cert and harvest
   the password on every poll (default: every 30 minutes, forever).

3. **File permissions.** `token.json` is written with default umask (644);
   `deploy.sh` already `chmod 600`s `.env` (line 445), but `token.json` and the
   DB are not covered.

## Solution

### 1. Encrypt `credentials` at rest (AES-256-GCM)

New module `lib/secret-box.js`:

```js
// key: CREDENTIALS_KEY in .env — 64 hex chars (32 bytes). Generated by deploy.sh.
encrypt(plaintext)  -> 'enc:v1:' + base64(iv | ciphertext | authTag)
decrypt(stored)     -> plaintext; passthrough if value doesn't start with 'enc:'
isEncrypted(stored) -> boolean
```

- AES-256-GCM, random 12-byte IV per encryption, node `crypto` only — no new deps.
- **Single choke point:** credentials are read in ~5 places
  (`lib/mail-manager.js`, `lib/tools.js:773,808`, `index.js:670`,
  `lib/api.js` accounts CRUD). Add `getAccountCredentials(accountId)` /
  `setAccountCredentials(accountId, obj)` helpers in `lib/mail-manager.js` (or
  `lib/db.js`) and route every reader/writer through them; do the
  encrypt/decrypt only there.
- The `'enc:'`-prefix passthrough makes migration lazy and rollback-safe:
  old rows decrypt as plaintext; every write re-encrypts. Add a one-shot
  startup sweep (`UPDATE` each plaintext row once) so old backups age out
  after 7 days.
- Missing `CREDENTIALS_KEY` with encrypted rows present → fail loudly at
  startup with a clear operator message (do not silently drop mail accounts).
- deploy.sh: generate the key (`openssl rand -hex 32`) into `.env` for new and
  existing instances; update `.env.example` and `docs/deploy.md`.

**Honest scope statement (document in README/deploy.md):** the key sits in
`.env` on the same host, so this protects the *backups and Drive copies*, not
against a root-compromised VPS. The operator can still read tenants' mail —
that's the declared trust model; say it explicitly in the privacy section.

### 2. Make TLS verification the default

- Add `allow_invalid_tls` (boolean, default `false`) to the per-account
  credentials object.
- `lib/imap.js`: `tlsOptions: { rejectUnauthorized: credentials.allow_invalid_tls !== true }`
  in all 4 IMAP sites and the same for `smtpConfig()`. Extract a shared
  `imapConfig(credentials)` helper while touching this — the 4 copies of the
  connection object are already drift-prone.
- `lib/api.js:688` (connection test): same flag; the Mini App account form gets
  a "разрешить самоподписанный сертификат" checkbox (off by default) so the
  escape hatch exists for exotic home servers.
- Expect breakage only for servers with genuinely invalid certs — that
  breakage is the feature.
- **Important gotcha, found while implementing this against the live instance's
  real accounts:** the `imap` npm package does not set SNI (`servername`) on
  the TLS socket it opens. Without it, Node's TLS layer fails to verify even a
  perfectly valid certificate — reproduced directly against `imap.gmail.com`
  (a real Google-issued, CA-signed cert): with `rejectUnauthorized: true` and no
  `servername`, the connection fails as `"self-signed certificate"`; with
  `servername: credentials.host` added, it verifies correctly. **Both
  `tlsOptions` in `lib/imap.js` and `lib/api.js`'s connection test must set
  `servername` alongside `rejectUnauthorized`, or flipping the default to
  secure will break every legitimate account, not just the insecure ones.**
  This is not a hypothetical — the live instance's two IMAP accounts (both
  pointed at `imap.gmail.com`) failed exactly this way before `servername` was
  added.

### 3. File permissions

- `lib/google.js:47` and any other `token.json` writers:
  `fs.writeFileSync(TOKEN_FILE, data, { mode: 0o600 })` + one-time `fs.chmodSync`
  on startup if the file exists with wider perms.
- deploy.sh / update.sh: `chmod 600 token.json data/snezhanna.db 2>/dev/null || true`.

## Non-goals

- Encrypting the whole DB (SQLCipher) — disproportionate; credentials are the
  only secret column.
- KMS / external secret storage — SaaS-tier concern.

## Acceptance criteria

1. `sqlite3 data/snezhanna.db "SELECT credentials FROM email_accounts"` shows
   only `enc:v1:...` values after one startup on the new version.
2. A Drive backup downloaded and opened with sqlite3 contains no plaintext
   passwords or OAuth refresh tokens.
3. Mail polling, send, drafts, attachments, `/auth2`, Mini App account CRUD and
   connection test all work unchanged for both gmail and imap accounts.
4. IMAP connection to a server with a self-signed cert **fails** by default with
   a readable error, and succeeds with `allow_invalid_tls: true` on that account.
5. `ls -l token.json data/snezhanna.db .env` → `-rw-------` for all three.
6. Deleting `CREDENTIALS_KEY` from `.env` produces a clear startup error, not
   silent misbehavior.
