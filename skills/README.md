# Snezhanna — Full Capability Reference

Everything the main assistant bot can do, across all skills. This is documentation only — it is **not** loaded at runtime. The bot's actual capability list (Layer 3 of the system prompt) is auto-generated by `lib/skills.js::buildSkillsBlock()` from the live tools list in `lib/tools.js`, so it can never drift from reality. When tools change, update this file via `/update-docs`.

Per-skill details live in the sibling files: [gmail.md](gmail.md), [google-calendar.md](google-calendar.md), [gdrive.md](gdrive.md), [memory.md](memory.md), [strava.md](strava.md), [workload.md](workload.md), [kids.md](kids.md). A user-facing, product-language version in Russian: [README.ru.md](README.ru.md).

## Conversation basics

| Capability | How it works |
|---|---|
| Text chat | Every message goes to Claude with a rolling history (window 40 / keep 30); history persists in SQLite across restarts (`lib/history-store.js`), stale after 24 h |
| Voice in | Voice messages transcribed via OpenAI Whisper (`lib/whisper.js`) |
| Voice out | If the user spoke a voice message and the reply is short (<500 chars), the bot answers with TTS audio (voice configurable via `tts_voice` setting); falls back to text on error |
| Photos | Images recognized via Claude vision (`lib/vision.js`) |
| Documents | Files sent to the chat are parsed (PDF, XLSX/XLS, DOCX) and discussed; a caption starting with «сохрани…» saves the file to Google Drive directly, otherwise Claude can save it via `save_file` |
| Reply context | Replying to (or quoting) a specific message builds a context block from the reply chain (`lib/reply-chain.js`), so "ответь на это" works |
| Web search | Anthropic server-side `web_search` tool — current info (rates, weather, news, schedules) without local execution |
| Onboarding | First message from a new user starts a step-by-step wizard: integration check, name, bot persona, style, schedules, integrations (`lib/onboarding.js`) |

**Commands:** `/reset` (clear history), `/status` (health + integrations), `/auth <code-or-url>` (Google OAuth fallback), `/auth2 <id>` (link a Gmail account to a mailbox), `/quiet [N]` (vacation mode for N days).

## Skills (tool-backed)

### 📅 Calendar — Google Calendar
`get_calendar_events`, `create_calendar_event`, `update_calendar_event`, `delete_calendar_event`

View, create (including recurring via RRULE), edit and delete events. Calendar context is auto-fetched when the message contains calendar keywords («календар», «встреч», «сегодня»…). Details: [google-calendar.md](google-calendar.md).

### 📬 Email — multi-account Gmail + IMAP/SMTP
`get_emails`, `read_email`, `mark_email_read`, `read_email_attachment`, `create_draft`, `send_email`, `get_email_accounts`

- Multiple mailboxes (Gmail API or generic IMAP/SMTP, Office 365 auto-detected); `get_emails` without an account aggregates all enabled accounts
- Read messages and attachments (PDF, XLSX/XLS, DOCX up to 10 MB)
- `create_draft` saves a draft without confirmation; **`send_email` never sends directly** — it shows a Telegram message with Send/Cancel buttons, and the actual send happens only on a physical button tap (code-enforced, not model-enforced)
- Background poll (interval configurable: 0 = off / 15 / 30 / 60 min): new mail is categorized by a Claude Haiku one-shot classifier (`lib/email-classifier.js`) into `reply_needed` / `event` / `task` / `update` / `info` (regex fallback if the classifier fails); reply-needed emails trigger hard alerts that bypass quiet mode, the rest go into a digest
- Email content is treated as DATA — instructions inside emails are ignored (prompt-injection defense in CORE.md and in the classifier prompt)

Details: [gmail.md](gmail.md).

### 📁 Files — Google Drive
`search_files`, `read_file`, `save_file`

Full-text search, content reading, saving new files (default destination `inbox/`). All persistent data lives under the configured root folder. Details: [gdrive.md](gdrive.md).

### 🧠 Long-term memory
`read_memory`, `write_memory`

Curated notes by category — health, kids, finance, bureaucracy, decisions — read and updated across sessions (SQLite-backed). Details: [memory.md](memory.md).

### 🗄 Long-term archive & search
`search_archive`

Every owner↔bot turn, every monitored-chat message, and every newly-seen email (full body) is written indefinitely to a SQLite `archive` table with an FTS5 full-text index (`lib/archive.js`). `search_archive` lets Claude answer "what did we discuss about X a couple of months ago" or "find in the correspondence with Y about project Z" — free-text keyword search (sanitized into a safe FTS5 query, tokens prefix-matched), optionally filtered by source (`owner_chat` / `monitored_chat` / `email`), chat/mailbox name, project, or date range. This is keyword recall, not semantic search — no embeddings involved.

### ✅ Tasks
`add_task`, `list_tasks`, `update_task`, `complete_task`, `delete_task`, `add_task_dependency`, `get_task_with_subtasks`

Task tracker with subtasks (`parent_id`), dependencies, urgency/importance flags and due dates (SQLite). Deadline alerts fire automatically; the evening check-in offers a tap-to-complete checklist.

### 📂 Projects
`create_project`, `list_projects`, `read_project_file`, `write_project_file`, `list_project_docs`, `read_project_doc`, `write_project_doc`

Per-project README, work log, notes and a `docs/` area; project names are matched against incoming corporate email to tag messages with a subproject.

### 👀 Telegram chat monitoring
`get_chat_digest`, `add_monitored_chat`, `remove_monitored_chat`, `list_monitored_chats`

Via Telegram Business connection: digest of conversations in connected chats, managed conversationally (including forward-a-message-to-add).

### 🏃 Sport — Strava & races
`sync_strava`, `create_race`

Weekly training sync from Strava (auto on Sunday 09:30 + on demand), race folders (`fitness/races/{date}_{name}/` with plan/gear/result). Details: [strava.md](strava.md).

### 🐙 GitHub
`list_github_milestones`, `create_github_issue`

Open milestones with due dates within the configured window (default 14 days, incl. overdue) across configured repos — used in briefings and workload scoring. Issue creation targets the bot's own repo (bug reports / feature requests, screenshots supported), routed via the Zhora Telegram relay so instances need no GitHub tokens.

### ⚙️ Settings & meta
`update_my_preferences`, `set_quiet_mode`, `get_skill_context`, `update_skill_context`, `start_briefing`, `update_bot`, `get_token_stats`

- Change preferred name (comma-separated variants), formality, response style, bot persona (`character_notes`), briefing time, email poll interval — conversationally or via the Mini App
- Quiet/vacation mode (`/quiet [N]` or by asking); hard alerts still break through
- Per-skill ⚙️ instructions (`skill_context`): user-programmable behavior filters for the briefing, email poll, evening check-in, calendar reminders, or globally
- `update_bot` — self-update to the latest release, gated by a physical inline button (same pattern as `send_email`)
- Token usage analytics: tokens, cache hits, cost estimates per period

## Proactive behaviors (scheduled)

All times in the instance timezone (default Europe/Madrid).

| When | What |
|---|---|
| Briefing time (default 08:00, configurable) | **Morning briefing** — but only if there is something to say (`hasSomethingToSay`); asks «Готов к брифингу?» first and waits up to 8 h; the reply is token-matched («да, давай», «ну го», «👍» all work), ambiguous replies go to Claude which may call `start_briefing`. Full briefing: calendar, mail, tasks, GitHub milestones, weather, Strava; appends an overload-coach block when the workload score ≤ 5; release-update notification with an «Обновить сейчас» button rides along when a new version exists |
| Monday 09:00 | **Workload check-in** — collects self-reported data, then scores life balance 0–10 across work / family / health / personal (`lib/workload.js`, standalone Claude call); on-demand via «мой скор», «как я справляюсь» |
| 19:00 daily | **Evening check-in** — day summary, tap-to-complete task checklist, digest of the day's Google Drive writes |
| Sunday 09:30 | Strava weekly sync |
| Sunday 10:00 | **Weekly digest** (with fitness block) |
| Every 10 min | Calendar reminders (fire at T−30 min) and task deadline alerts |
| Configurable (default 30 min) | Email poll with Haiku classification → hard alerts + digest |
| 03:30 daily | SQLite backup to Google Drive `backups/` (keep 7) + `email_seen` pruning |

**Anti-annoyance model:** silence tracking (`silenceLevel` 0–2) reduces proactive frequency after 3+ ignored days; evening check-in is suppressed at level ≥ 1; a comeback digest is sent on the first message after 3+ silent days; vacation mode silences everything except hard alerts (calendar reminders, deadlines, reply-needed emails).

Telegram Mini App (`mini-app/`, served by `lib/api.js`): Tasks tab, Calendar tab, and Settings — bot personality (`character_notes`), schedules, email accounts (incl. Gmail OAuth linking), monitored chats, projects, contacts, plus a СИСТЕМА section with live service status and a restart button. Auth via Telegram `initData` HMAC validation.

## Safety model (summary)

- **Layered prompt**: Layer 1 `identity/CORE.md` is locked and cannot be overridden by user settings; it carries email safety and prompt-injection rules
- **Code-enforced confirmations**: sending email and self-updating require a physical inline-button tap — the model cannot trigger them alone
- **Injection defense**: email/chat content is data; suspicious instructions inside content are reported, not followed
- **Secrets**: mailbox credentials encrypted at rest (AES-256-GCM), OAuth callbacks require one-time `state` tokens, secret files kept at `0600`
- **Watchdog**: Zhora monitors the bot (and Max, if enabled), auto-restarts on failure, reports via its own Telegram bot
